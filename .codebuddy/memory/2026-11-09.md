## W-05 第三批：animation 关键帧插值（用户「继续」，2026-11-09）

**Why**：用户连续多轮要求「继续」，按 `PRIORITY.md` 的 P0 关键路径，ripple 与 placement 两批之后继续翻译经典版纯函数，累积领域回归网，为 W-06 的 Web 绑定铺路。

**交付**：`local/crates/ocx-domain/src/animation.rs`（贝塞尔求解 4 函数 + interpolation 的归一化/外推/三种段求值/离散通道/统一分派），配套 `tests/{animation_golden_master.rs,animation_unit.rs,animation-reference.mjs,animation-alignment.test.mjs,ANIMATION_CASES.md,fixtures/animation_cases.json}`。经典版路径是 `apps/web/src/animation/{bezier,interpolation}.ts`；`keyframe-query.ts` 依赖 `channel-data.ts` 与 `params` 颜色格式化，本批不做并已注明。

**关键决策（跨语言浮点）**：经典版 `solveBezierProgressForTime` 只做 20 次二分，固有误差约 `4.8e-7`，经数值缩放后约 `5e-6`。最初设 `1e-9` 容差会误判，改为 **`1e-5`**（仍远小于任何逻辑错误）。Rust 与 JS 两侧都实现**递归容差比较**：数值按绝对误差、对象/数组逐项、其余严格相等。这解决了 `serde_json::Number` 的 `Float(0.0)` 与 `PosInt(0)` 不相等、以及跨语言最短小数表示差异两类问题。

**判别方式差异**：经典版 `isScalarChannel` 靠 `extrapolation` 字段或 key 的 `segmentToNext`；Rust 用 `#[serde(untagged)]` 按 value 的数值/布尔字符串类型判别，JSON 结构保持经典版原样（无额外 `kind` 字段）。语义等价并记录在 `NOTICE.md`。

**验证**：四 crate `fmt --check` / `clippy -D warnings` / `cargo test` 全绿；`moon run ocx-domain:test`（proto 管理、无 FORCE_GLOBALS）退出码 0；JS 三套对齐 **animation 88/88、placement 100/100、ripple 64/64**，契约 5/5、看板 44/44、兼容契约 45/45；42 个文档链接 0 失效；lints 0；代码文件均 ≤500 行。累计 72 个 JSON golden 用例、13 个补充单测。

**踩坑**：clippy `unnecessary_sort_by` 两处改 `sort_by_key`；`animation_unit.rs` 初版把稳定排序后的帧顺序断言写错（实际 a→c→b），已修正。

**How to apply**：继续按同一模板（JSON fixtures + Rust golden master + JS 参考实现 + CASES.md + 补充单测）翻译剩余领域逻辑；每次新增浮点结果都要评估迭代算法固有精度再定容差。下一批可做 `keyframe-query` 或转向 W-06 Web 绑定薄层。

## W-07 第一批：帧契约 + 预览帧（用户「按你的建议做」，2026-11-09）

**Why / 方向调整**：上一轮我把 W-07 列为首选，但核对 `PRIORITY.md` 后发现两点：① W-06 的 DoD 是「`/editor` 能加载项目、显示时间轴与**预览帧**」，上一批只做了时间轴，预览帧缺失；② W-07 完整 DoD 是导出 MP4/WebM 并校验帧数/音画同步，前置依赖 H01/H05 的 GPU 渲染路径（仍未验证）与浏览器 `VideoEncoder` + muxer 自动化。直接做完整导出会产出无法验证的半成品。因此本批做**可确定性验证的契约切片**，同时补齐 W-06 的预览帧。

**关键决策**：`RenderFrame` / `ExportProfile` 是**本地新契约**（不是经典版 TS 翻译），所以沿用 W-05 的 JS 参考实现没有意义；改为 Rust golden master（26 个 JSON 用例 + 5 个单测）+ Node 真实 WASM 契约测试（28/28）双层验证。经典版 `services/renderer/compositor/frame-descriptor.ts` 是渲染节点树描述，`scene-exporter.ts` 依赖 `mediabunny`，两者都不适合直接搬，已核对但未复制。

**交付**：
- `local/crates/ocx-render`：`profile.rs`（容器/编码组合、偶数尺寸、码率、音频参数校验 + 5 个稳定错误码）、`plan.rs`（帧数向上取整、帧时刻、**累积采样数** `floor(i*denominator*sampleRate/numerator)` 保证 29.97fps 无漂移、10000 帧上限）、`frame.rs`（`RenderFrame` RGBA8、确定性合成帧、FNV checksum、越界保护）。
- `ocx-bindings-wasm` 新增 `validateExportProfile` / `buildFramePlan` kind 与 `render_frame_rgba`（直接返回 `Vec<u8>` → JS `Uint8Array`，避免 base64 膨胀）。
- `editor-adapter.ts` 扩展至 7 种 kind + `validateFrameRequest` + `renderFrameRgba`（I-01 仍是唯一入口）；新增 `webcodecs.ts` 能力探测（异常转可读结果，不抛）。
- `/editor` 新增 canvas 预览帧（core 生成 320×180 RGBA）+ 帧计划摘要 + WebCodecs 能力展示。

**验证**：六 crate `fmt --check` / `clippy -D warnings` / `cargo test` 全绿；Node WASM 契约 28/28（含 RGBA 逐点像素、帧随时间变化、非法 profile 拒绝）；vitest 10/10；`tsc` 本次文件 0 错误（3 个上游既存 `components/ui/*` 错误未动）；`vite build` 退出码 0；dev 端 `/editor` 与重建 wasm（497,956 B）HTTP 200。

**踩坑**：clippy 在 Rust 1.97 下要求用 `u32::is_multiple_of(2)` 替代 `% 2 == 0`；改 Rust 源码后**必须重建 wasm + glue 并同步提交两份 wasm**，否则前端加载旧 core（已按 H03 §9 约定执行）。

**How to apply**：下一步做真实导出时必须先确认 H01/H05 渲染路径与浏览器自动化方案；`moon ci` 仍不含 wasm 构建。看板数据版本 bump 至 `2026-11-08-r11`。
