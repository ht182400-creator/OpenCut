**Why**：用户连续多轮要求「继续」，按 `PRIORITY.md` 的 P0 关键路径，ripple 与 placement 两批之后继续翻译经典版纯函数，累积领域回归网，为 W-06 的 Web 绑定铺路。

**交付**：`local/crates/ocx-domain/src/animation.rs`（贝塞尔求解 4 函数 + interpolation 的归一化/外推/三种段求值/离散通道/统一分派），配套 `tests/{animation_golden_master.rs,animation_unit.rs,animation-reference.mjs,animation-alignment.test.mjs,ANIMATION_CASES.md,fixtures/animation_cases.json}`。经典版路径是 `apps/web/src/animation/{bezier,interpolation}.ts`；`keyframe-query.ts` 依赖 `channel-data.ts` 与 `params` 颜色格式化，本批不做并已注明。

**关键决策（跨语言浮点）**：经典版 `solveBezierProgressForTime` 只做 20 次二分，固有误差约 `4.8e-7`，经数值缩放后约 `5e-6`。最初设 `1e-9` 容差会误判，改为 **`1e-5`**（仍远小于任何逻辑错误）。Rust 与 JS 两侧都实现**递归容差比较**：数值按绝对误差、对象/数组逐项、其余严格相等。这解决了 `serde_json::Number` 的 `Float(0.0)` 与 `PosInt(0)` 不相等、以及跨语言最短小数表示差异两类问题。

**判别方式差异**：经典版 `isScalarChannel` 靠 `extrapolation` 字段或 key 的 `segmentToNext`；Rust 用 `#[serde(untagged)]` 按 value 的数值/布尔字符串类型判别，JSON 结构保持经典版原样（无额外 `kind` 字段）。语义等价并记录在 `NOTICE.md`。

**验证**：四 crate `fmt --check` / `clippy -D warnings` / `cargo test` 全绿；`moon run ocx-domain:test`（proto 管理、无 FORCE_GLOBALS）退出码 0；JS 三套对齐 **animation 88/88、placement 100/100、ripple 64/64**，契约 5/5、看板 44/44、兼容契约 45/45；42 个文档链接 0 失效；lints 0；代码文件均 ≤500 行。累计 72 个 JSON golden 用例、13 个补充单测。

**踩坑**：clippy `unnecessary_sort_by` 两处改 `sort_by_key`；`animation_unit.rs` 初版把稳定排序后的帧顺序断言写错（实际 a→c→b），已修正。

**How to apply**：继续按同一模板（JSON fixtures + Rust golden master + JS 参考实现 + CASES.md + 补充单测）翻译剩余领域逻辑；每次新增浮点结果都要评估迭代算法固有精度再定容差。下一批可做 `keyframe-query` 或转向 W-06 Web 绑定薄层。

## W-08 第二批：片段级素材映射，让剪辑真正改变画面（用户「继续」，2026-11-09）

**Why / 发现的语义缺口**：上一批虽然接进了真实素材，但 `frameSource` 一直按项目帧索引顺序 `mediaFrameAt(media, index)` 取帧，与片段无关——**删除片段只缩短时长，导出画面内容其实没变**。这不符合「编辑视频」的核心语义，本批优先修它（比音频调度更贴近用户关心的主线）。

**交付**：

- 新 `apps/web/src/local/timeline.ts`：`clipAtTime` / `mapProjectFrame`（项目帧时间 → `trimStart + (t - startTime)` → 素材帧索引，短素材循环复用、空档返回 null）/ `splitClipAt`（在播放头切两段，第二段 `trimStart` 累加、生成唯一 id）。`timeline.test.ts` 9 项单测，含「删除首片段后首帧改从素材 1s 开始」的核心断言。
- `editor.tsx`：`CoreElement` 带 `trimStart`；`frameSource` 改走映射（空档用不透明黑帧）；预览/导出共用；`deleteSelected` 后从原片段表恢复 `trimStart`（core 的 `TimedElement` 不含素材裁剪信息）；新增「在播放头分割」按钮与当前片段显示。
- `editor-wasm.contract.mjs` 加 trim 读取断言（47/47）。按约定重建两份 wasm（604,402 B）。

**决定性验证（两次导出对比）**：生成演示 mp4 → 未剪辑导出 90 帧 / 36,376 字节，重新解码首帧 hash `2010631942` → 删除 `clip-intro` 后帧 1/60、片段 `clip-body`、预览 hash 变化 → 再导出 60 帧 / 22,215 字节，重新解码首帧 hash `1357128289`（`ftyp` 有效）。**两次首帧不同，证明剪辑真正改变了导出画面**。分割验证：帧 46/90 处切 `clip-body` → 剩余 3 个片段，`clip-body#2: 180000 + 180000 ticks, trim=180000`（连续）。

**踩坑**：`timeline.test.ts` 一用例期望写错（项目 2s → 素材帧 60，`60 % 40 = 20` 而非 0），已修并加注释。

**How to apply**：新增剪辑动作（裁剪时长、拖拽移动）时，必须同步维护片段的 `trimStart` 与映射，否则画面又会与剪辑脱节；core `ripple` 只负责位移，不携带素材裁剪信息，前端需按 id 恢复。看板数据版本 bump 至 `2026-11-08-r15`。

## W-08 第三批：音频调度闭环（用户「继续」，2026-11-09）

**Why**：`PRIORITY.md` 把「音频调度」明确列为 W-08 风险栏，§4.5 还要求导出前做 `AudioEncoder.isConfigSupported({codec:"mp4a.40.2"})` 探测并覆盖「MP4 带音频」回归。前两批导出的 MP4 都是无声的，本批补上，W-08 主链路才算完整。先实测浏览器能力：`AudioEncoder`/`AudioData`/`AudioContext` 齐备，AAC 48kHz 双声道 `supported=true`。

**架构**：浏览器负责编解码，core 负责帧契约；音频侧沿用 W-07 `FramePlan` 的**累积采样**思路 `cumulative(i)=floor(i*sampleRate/fps)` 防非整数帧率漂移（29.97fps 得 1601/1602 交替，与 Rust `build_frame_plan` 的 48048 总量一致），但切片/编码在前端完成——诚实边界：尚未把 core 的 `audio_samples_per_frame` 数组直接接到导出器。

**交付**：

- `editor.tsx`：导出前能力探测，命中则 `buildTimelineAudio({clips: elements, ...})`（与视频帧映射同源，剪辑也改变声音）；素材状态显示「含音轨/无音轨」，导出结果标注「含 AAC 音轨」。

## W-09 第一批：代理帧缓存与量化（用户「继续」，2026-11-09）

**Why**：W-08 三批后主链路已闭合，按关键路径下一环是 **W-09 代理剪辑 + 预览帧缓存**（H12）。当前瓶颈是 `<video>` 逐帧 seek 抽帧（限 90 帧、每次导入重来），实测单次约 10 秒；4K 素材全尺寸解码后 `drawImage` 缩到 320×180 也浪费。

**交付**：
- 新 `apps/web/src/local/frame-cache.ts`：`buildCacheKey`（name/size/lastModified + 代理宽高/fps/frameCount，任一变化即失效）、`FrameCache` 内存 LRU（Map 插入顺序，命中时 delete+set 刷新，默认 3 份）、`cachedMediaBytes`、`stats()`（hits/misses/entries/cachedFrames/cachedBytes）、`clear()`；`frameCache` 单例。
- `media.ts`：`decodeVideoFile` 先查缓存，命中直接返回（`fromCache:true, decodeMilliseconds:0`），未命中才建 `<video>` 逐帧 seek + `decodeAudioFromFile`，完成后写缓存并记录 `performance.now()` 耗时；代理尺寸恒为 320×180；`DecodedMedia` 加 `fromCache`/`decodeMilliseconds`；新增 `clearFrameCache()` / `getFrameCacheStats()`。`createDemoVideoFile` 固定 `lastModified: 0` 让重复生成可命中同一 key。
- `editor.tsx`：导入后显示「代理帧 / 解码 Nms 或 代理缓存命中 · 0ms」、缓存统计，加「清除帧缓存」按钮；顶部说明更新。
- `frame-cache.test.ts` 8 项单测（key 稳定性与区分性、命中/未命中、LRU 淘汰、clear 保留累计、重复 set、字节统计、单例）。

**真实浏览器量化（决定性证据）**：首次生成演示素材 →「已载入 demo-clip.mp4 · 90 代理帧 · 2.01s · 含音轨 · 解码 **10370ms**」，缓存 `1 份 / 90 帧 / 20.5MB · 命中 0 / 未命中 1`；再次生成 →「**代理缓存命中 · 0ms**」，命中 1；点「清除帧缓存」→ `0 份 / 0 帧 / 0.0MB`。**重复导入省掉约 10.4 秒**。

**踩坑**：`DecodedMedia` 每次加字段（`audio`、`fromCache`、`decodeMilliseconds`）都会让 `media.test.ts` 的两处构造报 TS2739/TS2741，需同步补；上一批已把验证脚本 `TSC_OWN_FILE_ERRORS` 分类改成覆盖全部 `src/local/`，这次才第一时间发现。另：重写 `editor.tsx` 时一度把 `evaluate<RippleResponse>` 误写成 `evaluate<RippleAdjustment[]>`，已修。

**诚实边界**：本批是**代理帧缓存**而非「代理文件」（低分辨率 mp4），缓存只在内存、刷新即失效（未接 IndexedDB）；指纹非内容哈希（同名同大小同 lastModified 可能误命中）；W-09 DoD「设定量化阈值后 4K scrub 达标」仍需真实 4K 素材实测，本批量化的是重复导入解码耗时（阈值：命中 < 100ms，实测 0ms）。M6 时间线版本快照未做。

**How to apply**：后续加缓存失效触发点（素材内容变更、代理尺寸调整）时复用 `buildCacheKey`；若接 IndexedDB 持久化，注意 LRU 上限与 20MB/份的内存占用。看板数据版本 bump 至 `2026-11-08-r17`。
